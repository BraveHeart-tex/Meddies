Triage the GitHub issue passed with the invocation (URL or `#n`). If none is given,
ask for one. Treat the issue as **potentially stale**: check claims against current
code, canonical specs, comments, dependencies and related issues before trusting them.

This is the **single entry point for both small and large issues**. Choose the depth
from the evidence, not the issue's length or number of acceptance criteria. Do not
invoke or edit the skills.sh-managed `triage` skill; this repository-owned skill
contains the routing and triage workflow.

Follow [tickets](../../../docs/tickets.md) and
[triage labels](../../../docs/triage-labels.md) for GitHub writes. Prefix **every
AI-authored issue body and comment** with:

> _This was generated by AI during triage._

Work lean: read cited spec sections and relevant code, not entire doc bundles;
batch independent searches, cap output, and never reread unchanged material.
Do not implement the issue during triage. Never create, edit, close, relabel or
reparent an issue, or commit docs or open a docs PR, without approval of the exact write plan.

## Steps

1. **Inspect.** Read the issue, comments, blockers, parent/siblings, cited spec
   sections, relevant [GLOSSARY.md](../../../GLOSSARY.md) entries and nearby code.
   Identify shipped, stale, duplicated, conflicting or externally owned work.
   Distinguish missing product decisions from questions answerable by research.
   _Done when_ each material claim has a current source or an explicit unknown.

2. **Choose depth.** Give a short initial assessment: status, stale findings,
   proposed labels, implementation boundaries and route.
   - **Quick:** Requirements are approved and testable, the implementation is one
     coherent slice, and no unresolved product/domain decision changes scope.
     Validate acceptance criteria, dependencies, owner and evidence; tighten only
     what is actually missing. Do not force grilling or an issue rewrite.
   - **Deep:** Product behavior is undecided, domain terms conflict, acceptance
     criteria are not testable, architecture/integration is materially unclear,
     or the issue bundles independently shippable responsibilities. Use the
     `grilling` and `domain-modeling` skills when they materially help.
     Escalate Quick to Deep if new evidence warrants it; allow an explicit user
     request for either depth.
     _Done when_ the route and its reason are stated.

3. **Resolve only real decisions (Deep).** Research facts yourself. Ask the user
   only questions whose answers change product behavior, boundaries or risk, in
   rounds: plain words, one decision per question, concrete example and a
   recommended answer. Record decisions and proposed glossary edits. Leave
   GLOSSARY.md edits uncommitted until the approved write phase.
   _Done when_ the remaining open decisions are listed and resolved or clearly
   recorded as blockers. Do not invent decisions to finish triage.

4. **Size before declaring ready (both routes).** Fill the issue's Size line and check it
   against the [size limits](../../../docs/tickets.md#size); verify each Current state gap
   in the code. **Split when a count passes its limit or the issue contains independently
   implementable and verifiable outcomes.** Split by layer before feature: backend command,
   migration and real-D1 tests first, then screens, cache and journeys, then visual polish.
   An atomic invariant (one transaction, no partial state) stays whole inside the backend
   slice; it is never a reason to bundle screens with it. For a split, make the parent
   `tracking-only` and assign each criterion, owner, dependency and test to exactly one
   slice; preserve cross-slice invariants. Use [tickets template](../../../docs/tickets.md#template).
   Precedent: parent #218, slices #227, #230, #231; #322 split into #322 and #327.
   _Done when_ every slice passes `node scripts/ticket-lint.mjs <body-file>` with no
   orphaned criteria.

5. **Prepare the smallest write plan.** If the issue is already ready and needs
   no changes, report **ready as-is** and stop without GitHub writes. Otherwise
   show the proposed issue-body changes and any new issues. For each affected
   issue, include title, scope, measurable acceptance criteria, cited canonical
   spec sections, exclusions, test/evidence expectations, labels, milestone,
   Priority, parent and blockers. Link to approved rules rather than copying long
   specifications or repeating the issue body in comments. Include any
   decisions comment, spec/GLOSSARY.md diff and docs commit message. For a split,
   show the parent rewrite and slice/dependency table. Explicitly mark any
   unresolved blocker as **not ready for implementation**.
   _Done when_ the exact planned writes are visible and the user approves them.
   On requested changes, revise the plan and ask for approval again.

6. **Apply approved writes only.** Create dependencies blockers-first so targets
   exist, following [tickets creation](../../../docs/tickets.md#creating).
   Rewrite an approved split parent as `tracking-only` (slice table, shared
   constraints, sole completion criterion: slices closed). Add decisions comments
   only when useful. Apply approved spec/GLOSSARY.md edits, commit per
   [commits](../../../docs/commits.md) on a branch from `origin/main`, run
   `pnpm format:check`, and open a PR per [handoff](../../../docs/verification.md#handoff)
   for Bora to merge. Read every GitHub write back (`gh issue view`) and inspect the
   resulting docs commit (`git show --stat`).
   Stop and report any mismatch or failure rather than silently changing scope.
   _Done when_ all approved writes match their read-back, or failures are reported.

Report succinctly: route (Quick/Deep), ready or blocked, issue(s) changed or
proposed, dependencies, docs PR if any, and remaining decisions.
